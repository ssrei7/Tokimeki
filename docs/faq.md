# 项目答疑

这份文档记录使用体验、概念解释和讨论中的常见问题。它不是架构规范，也不替代 `AGENTS.md`、数据模型或路线图；确定后的技术约束仍以对应正式文档为准。

## 阶段 1 验收

### `custom-reputation` 是什么？

它不是 Tokimeki 已经定义好的正式属性，只是阶段 1 的演示 stat 名称，用来证明 `stats` 可以使用任意数字字段。当前 Mock 的 `perfect` fixture 会同时提出：

- `give_item`：给玩家一朵 `white-flower`
- `add_stat`：把玩家的 `custom-reputation` 从 0 增加到 2

因此，增加 2 不是“获得花必然增加声望”的游戏规则，而是为了在一次确定性验收中同时看到物品变化和通用 stat 变化。正式玩法中，是否因送花改变某个关系轴或其他 stat，要由阶段 5 的礼物规则和内核条件决定，不能由这个 fixture 推断。

### 自定义 stats 做什么？

自定义 stat 是玩家或世界的通用数字状态，例如 `money`、`trust`、`temperature` 或作者自定义的数值。阶段 1 的设置入口只负责创建或修改玩家 stat 的初始值；后续 AI 提出的 `add_stat` / `set_stat` 会经过白名单、schema、clamp 和单回合上限，再由内核写入。

它可以在游玩过程中生效：条件表达式、事件、礼物和关系规则可以读取这些值，前提是对应功能在后续阶段接入。阶段 1 目前只提供基础存储、操作和表达式封装，不自动赋予每个 stat 具体玩法含义。

用户可以随时修改初始值。修改是直接改当前存档的玩家状态，导出普通存档时会随存档一起保存。

字段名存储层支持中文，例如 `好感`；但当前 `expr-eval` 条件表达式的标识符语法不能直接解析中文成员名。需要被条件表达式引用的字段，当前建议使用稳定的 ASCII key（例如 `affection`），中文只作为 UI 显示名或描述。后续若要支持中文表达式，需要单独设计安全映射和迁移，不能在当前阶段偷偷改变表达式语法。

### 当前界面里物品栏和 Ops diff 在哪里？

- 物品定义和当前库存：`资料 → 物品定义`、`资料 → 物品栏（当前世界状态）`
- 状态变化 diff：生成回复后，打开 `设置 → 高级与调试 → Ops diff`
- Mock fixture：`设置 → 高级与调试 → Mock provider 验收工具`

当前分区是阶段 1 的结构性入口，不是最终信息架构。库存、角色、世界书和预设以后可以拆成独立页面、标签或手机终端 App；只要继续让 UI 读取同一份 `SaveFile`，不需要改变状态所有权。阶段 4 之前只优先保证结构清晰和可操作，不提前做最终视觉定稿。

### 你贴出的 Ops diff 对不对？

对。它表示：

- `stage: strict`：原始 `<ops>` JSON 一次解析成功，没有用修复或抽取回退
- `parsedOps`：包含一个 `give_item` 和一个 `add_stat`
- `applied: 2`：两个操作都通过校验并执行
- `changes`：库存从 0 到 1，`custom-reputation` 从 0 到 2
- `warnings`、`rejected`、`truncated` 都为空或 0：没有未注册 op、拒绝、clamp 或单回合截断

这里的 `description` 是调试用的人类可读说明；真正的状态事实由 `changes` 的路径和值以及最终存档持有。

### 实际游玩时，物品定义必须先存在吗？

必须。`ItemDef` 是物品的目录定义，`player.inventory` 只保存 `itemId`、数量和获得来源。任何写入库存的 op 都先检查 `world.items[itemId]`；找不到定义就拒绝该 op、记录 warning，不会偷偷创建一个只有名字的物品。

物品定义的来源有三类：世界包/事件包或 scenario 预先提供，用户在资料页创建，或者后续阶段由受校验的数据包导入。导入时先做 schema 和引用完整性检查；运行时仍保留 op 层校验，防止 AI 或损坏数据绕过目录。

### 世界包是世界书和预设吗？

不是。世界书是 prompt 内容条目，资料页的预设主要是文风和提示词模板（可带生成偏好覆盖），它们目前由本地 IndexedDB 单独管理。**世界包**是后续阶段规划的数据包，面向一个可分享的完整世界，可能包含地图、角色、世界书、物品、事件和关系规则。它会通过 `manifest.type = 'world'` 和各自 schema 校验后导入，不能把普通世界书文本直接当成物品目录。

阶段 1 暂不承诺稳定的世界包导入格式；当前可用方式是资料页创建物品，或使用 scenario/测试代码预先播种。后续会提供模板，概念上类似：

```json
{
  "items": {
    "white-flower": {
      "id": "white-flower",
      "name": "白色小花",
      "tags": ["flower"],
      "description": "一朵小花",
      "giftable": true
    }
  }
}
```

这只是字段示例，不是当前阶段可直接导入的最终世界包文件。

### scenario 是剧情吗？

不是。scenario 是版本感知、可重复生成的**存档起点工厂**，例如“第 40 天、玩家在码头、已有 5 个物品定义”。它可以带初始物品目录和库存，也可以通过普通 `save.zip` 导出；它不代表玩家已经经历的剧情过程，也不能替代事件包或角色卡。

### 事件包是什么？

事件包是可导入的 `EventDef` 数据集合。事件通常就是玩家在地图上到达某地点、处于某天/时段、遇到某角色后触发的剧情事件，也可以是导演排程的预约事件或纯静态 `content` 事件。事件定义可以声明触发条件、冷却、权重、场景提示和经过校验的 ops；事件包不是世界书，也不是聊天记录。

事件包引用物品时，必须同时引用已经存在的 `ItemDef`，或者在未来支持的动态物品 op 中先原子注册定义再发放。

### 如何判定“角色把哪件物品交给玩家”？

不能从正文猜。确定性判定需要同时满足：

1. 对话上下文有当前角色 `actorId`。
2. AI 提出的 op 携带已存在的 `itemId` 和数量。
3. 该 op 通过注册表 schema、物品定义、数量 clamp 和单回合上限校验。
4. 正式礼物系统接入后，还要通过阶段、心情、标签和角色规则；来源角色必须与当前 actor 匹配。

阶段 1 的 `give_item` 允许 `from` 省略，是为了支持通用奖励和 Mock fixture。阶段 5 的礼物系统应提供更明确的角色赠送路径，并要求来源角色明确、规则由代码计算。

### `ItemDef` 是精确物品还是分类？

当前 `itemId` 是精确引用，`tags` 只是分类和规则匹配。例如目录只有 `flower` 时，`give_item: flower` 会得到一个名为“花”的物品；它不会自动把“黄色小花”当成同一物品，也不会凭 tag 自动生成新物品。

如果要保留颜色、品种或剧情来源，应定义独立变体，例如 `flower-yellow`，名称写“黄色小花”，tags 写 `["flower", "yellow"]`。如果剧情不需要这些细节，也可以由规则明确把它归一化为通用 `flower`。这两种行为必须由数据/规则决定，不能由 AI 自行选择。

### 会不会“正文说递给你，但物品栏没有”？

会出现“叙述与状态提议不一致”，但不能让它变成静默的错误事实。项目的处理原则是：

- 只有成功应用的 op 才能进入物品栏；正文不会直接写库存。
- 缺少 `give_item`、物品定义不存在、来源角色不匹配或规则拒绝时，正文仍可显示，但物品栏不变，Ops diff/状态提示必须显示未产生状态变更或拒绝原因。
- 不能为了“修正”正文而从自然语言自动猜物品并入库；这会把不可信的 AI 文字变成事实。
- 后续礼物/事件流程应优先让内核生成可选的结构化互动结果，再让 AI 描述已确认的结果，从源头减少这种落差。

因此，阶段 1 验收的“递给你一朵花”不是靠文字识别，而是靠同一回复中的合法 `give_item` op 和 `changes` diff 证明。

### 预先定义物品，会不会失去随机惊喜？

不会。预先定义的是“可被系统认识和保存的候选池”，不是每次出现的固定顺序。后续礼物系统可以根据角色偏好、tag、阶段、心情、事件条件和固定 seed，从候选池中选择一件或一组物品；玩家每次遇到的具体结果仍可以不同，同时保持可复现、可回放和可验证。

随机性应由内核选择候选项，再让 AI 描述已经确认的结果；不能让 AI 临时发明目录外的物品来制造惊喜。阶段 5 先做规则化礼物候选与特殊物品，阶段 7/8 再扩展角色自有物品的携带、使用和事件联动。

### 用户如何确认当前物品目录？

阶段 1 在 `资料 → 物品定义` 列出当前 `world.items` 的 ID、名称和 tags；这里是“系统认识哪些物品”的权威目录。创建世界书、地图或角色卡时，提到一个物品不会自动加入目录。当前要确保引用有效，需要先在物品定义表创建它，或让 scenario/受校验的数据包一起提供它。后续世界编辑器应增加物品引用选择器和导入前完整性检查，避免作者只在自由文本里写出物品却忘记登记。

### 能否让剧情中获得的任意物品都进入物品栏？

可以实现，而且与地图为主并不冲突；难点是保持可校验和可导出。推荐在阶段 5/7 设计受限的动态物品流程：AI 提出带有名称、稳定 ID、tags 和来源的“注册并发放” op，内核校验字段、长度、重复 ID 和单回合上限，然后在同一事务中写入 `world.items` 和 `player.inventory`。如果注册失败，两者都不写入。

这能覆盖剧情临时出现的“黄色小花”“旧钥匙”等物品，但仍不应直接从自然语言自动提取。正文只是一种描述；必须有成功的结构化 op 才能成为事实。这样既保留任意剧情物品的灵活性，也避免同一物品被 AI 拼出多个目录 ID、无法堆叠或无法回溯来源。

### 如果物品栏主要是收藏，能否让自然语言提取后由用户确认？

可以，这是更合适的低风险路径。自动提取只生成“可能获得的收藏候选”，显示名称、描述、标签和来源；用户确认、编辑或删除后，内核才把它写入收藏。确认前不进存档，也不影响正文。建议把收藏型条目和会改变剧情/数值的功能性物品分开：前者允许自由编辑，后者仍必须经过明确 op、引用检查和效果规则。

### 终端许愿机适合怎么做？

可以作为阶段 9 的终端 App，但应当是显式的便利工具，不是任意状态写入后门。愿望先生成影响预览，用户确认后再执行；默认优先支持收藏品、重放已解锁内容等不改变世界事实的便利。涉及金钱、关系、事件进度或功能性物品时，应由世界规则授权，或仅在 sandbox 模式开放并留下记录。详细范围记录在 `docs/ideas.md`。

### 多个资料预设可以作为一个整体导入导出吗？

可以。资料页提供“预设包”，把多个文风/提示词预设放入同一个 zip；导入时逐项校验，ID 相同的预设按导入内容更新。单项 JSON 导入导出仍保留，方便只分享一个预设。

### 世界存档可以不带聊天吗？导入后能从零开始玩吗？

可以。导出世界存档时可以取消“包含聊天记录”，这样 zip 仍包含世界状态、角色卡、世界书和预设，但不包含聊天记录；这不会删除浏览器里已有的本地聊天。资料页也提供“清除全部聊天”，需要用户显式确认，清除后不影响角色卡、世界状态或其他资料。导入不带聊天的存档同样不会自动删除当前聊天，避免意外丢失；想从零开始时，导入后再点击清除即可。

### 多个预设如何切换？

预设条目和预设包分为两层：条目是包内可编辑的提示词片段，`PresetBundle` 才是资料页里的独立选项。用户切换预设包后，包内所有条目会合并注入下一次生成；条目不会单独切换或单独生效。选择“不使用预设包”则不注入资料预设。预设包导入导出不会覆盖 Provider 配置。

### 为什么无头 Mock 能在几秒内跑 20 个游戏日？

偶遇权重本身由 `core/` 的纯代码计算，不需要每个 NPC、每个 tick 调模型。无头 runner 直接在 Node 中批量创建固定 seed 的世界，推进天数、移动、日程和偶遇；只有确实需要叙述的节点才使用零 API 的 Mock provider。20 个 seed × 20 天可以并行或顺序快速完成，并输出相遇次数、最长未见间隔等统计。与 UI 无关，因此不会受浏览器渲染和人工操作拖慢。

### 后期调整偶遇权重会不会很麻烦？

不会。权重、保底间隔、移动触发开关和急事选择应作为数据/规则配置，由无头 runner 做固定 seed 回归。调整通常只改配置或数据包，然后重新跑报告；核心循环和界面不需要重写。新增一种触发方式仍需遵守注册 op、事件钩子或数据包边界。

### 偶遇可以发生在离开地点时吗？可以用急事当借口离开吗？

可以，计划放在阶段 4。玩家或角色离开地点时按开关和概率抽取偶遇，关闭开关后不触发。玩家准备离开时可以选择以“有急事”为借口离开，也可以留下并继续对方事件；两种选择都由内核记录，AI 只描述已确定的结果。

### 剧情上必须起作用的物品，如果不在物品目录/物品栏，会不会失效？

不会。需要区分两种状态：

- **收藏物品**：玩家获得并留下的条目，显示在收藏/物品栏中，可以被玩家主动出示给角色或 NPC。
- **剧情道具与线索事实**：事件包或内核事件状态声明的事实，例如现场的一把钥匙、某份证词或一次性线索。它们可以只存在于事件上下文、事件记录或已确认的剧情 flags 中，不依赖玩家收藏。

事件所需的剧情道具必须由代码或事件包声明，不能因为 AI 正文提到它就自动变成事实。收藏条目和剧情事实可以互相引用，但不能互相替代。这样即使玩家没有收藏某件道具，事件仍能按规则推进；如果玩家确实拥有收藏条目，则可以通过“出示证物”触发该角色/NPC 对应的确定性反应。

### 已触发的剧情事件能否像恋爱冒险游戏一样回看？

可以，计划放在阶段 7 的事件系统中。每次事件结束保存事件 ID、标题、时间地点、参与者、玩家选择、结果摘要和可回看的叙事记录。回顾资料可导出或删除；删除只删除回顾内容，不撤销事件已经造成的关系、flags、物品或其他世界变化。具体字段和长度控制会随 `world.eventHistory` schema 一起确定。

### 收藏物品的标题和描述可以按实际情况生成并由用户纠错吗？

可以。物品被确认进入收藏时，可以根据事件来源、获得地点、角色和当时叙述生成标题、描述、tags 与获得时间；用户随后可以修改展示文字或删除收藏。建议保留稳定的 `itemId`、来源和规则标签作为不可漂移的内核事实，避免用户改名后破坏礼物、事件或历史引用。

### 角色/NPC 出示物品时会参考哪些信息？

出示动作先由内核确认玩家拥有该收藏条目，然后将以下信息交给反应规则和叙述层：角色个性、当前 situation、关系/事件阶段、物品的规则 tags，以及用户当前确认的物品标题和描述。这样不同角色可以对同一物品做出不同反应；用户编辑描述会影响“对方看到的说法”，但不会凭空改变物品的功能效果或已经发生的剧情事实。

如果没有对应反应规则，角色可以只表现为观察、疑惑或普通评论，不应因为 AI 看到了描述就自动产生新的状态变化。

## Mock fixture 速查

| fixture | 预期结果 |
|---|---|
| `perfect` | 正文显示；白色小花 +1；`custom-reputation` +2；Ops diff 有 2 条变更 |
| `malformed` | 正文保留；解析失败；无状态变化；显示重试和手动补录 |
| `fenced` | 正确去除 Markdown 围栏；空 ops；无状态变化 |
| `unregistered-op` | 未注册 op 丢弃；合法 `set_flag` 仍执行并产生警告 |
| `clamp-exceeded` | `delta: 100` 被限制为 `+10`；Ops diff 显示 clamp 警告 |
| `empty-ops` | 解析成功但数组为空；无状态变化，不算失败 |
| `interrupted-stream` | 显示已收到的正文；请求失败；可重试状态提取 |
