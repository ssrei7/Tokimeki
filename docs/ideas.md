## 手机热点 / 活动 App

- 在网页自带的手机/终端中提供一个查看当前世界热点、活动与公共消息的 App。
- 内容既可以由 AI 生成，也可以由用户手动编辑；用户可从热点详情进入地点并触发对应活动。
- 先作为想法收纳，不并入当前阶段；后续评估数据结构、权限校验、活动触发条件与 API 调用频率后再进入路线图。

## 用户创意工坊 / 玩法包

- 允许用户为世界制作钓鱼、种田、开店等活动，并导出分享给其他用户安装。
- 玩法包只能组合数据包、声明式安全表达式、已注册 op、事件钩子与 prompt block，必须服从 `AGENTS.md` 的状态写入和联网边界。
- 阶段 1 建立 op/钩子基础，阶段 3/7/8 补足地图、事件、生活玩法能力，阶段 10 再评估包清单、安装卸载、版本依赖、权限展示、完整性检查与分享工作流。
- 自定义 UI 只考虑受限组件模板或沙箱化插件 API；安全模型、迁移与权限体系明确前不开放任意代码插件。

## 全局备份

- 在普通世界存档之外，评估全局备份功能，覆盖角色卡、世界书、预设、聊天与非密钥 Provider 元数据。
- API key 默认排除；若未来支持密钥备份，必须由用户显式选择并采用加密导出，导入时逐项提示覆盖范围。
- 阶段 0 的 `save.zip` 继续保持可分享、无密钥、不会覆盖 API 设置的边界。

## 资料条目的纯文本导入

- 后续为角色卡、世界书和预设条目增加 `.txt` 与 `.docx` 导入；两种格式都视为普通文本，不做字段映射，正文完整写入对应的“描述”文本框，名称等元数据仍由用户在界面确认或编辑。
- `.txt` 可用浏览器本地读取，不需要新增依赖；`.docx` 需在浏览器本地解压并提取 `word/document.xml` 正文，或在确认后引入固定版本的轻量解析依赖。两者均不调用 API、不上传文件。
- 该能力属于阶段 5 之后的资料兼容性增强切片，不并入阶段 4，也不改变世界状态 schema；实现时应补充导入失败提示、超长文本处理和最小格式保留（段落/换行）测试。

## 沉浸式聊天 App 界面

- 阶段 4 角色立绘、头像和多人同场能力落地后，将聊天视图作为独立 UI 垂直切片，做成接近真实手机聊天 App 的体验。
- 默认采用连续的短气泡回复，而不是单条长文：角色可将一次回复拆为数条短消息，逐条稳定显示，并保留长文本作为可选叙事模式。
- 规划联系人/会话入口、角色头像与状态、日期时间分隔、消息状态、输入区与软键盘适配，以及长消息和流式回复的稳定滚动。
- 阶段 0 只修正信息架构、请求状态与消息交互，不提前视觉定稿，避免后续头像与多人协议落地时返工。
- 在线状态、正在输入、已读等表现必须有明确的数据来源或标为纯展示反馈，不能伪造确定性状态或额外触发 API。

## 玩家衣柜与服饰描述

- 可行。玩家可维护自己的衣柜，服饰先作为文字描述与标签，由确定性状态持有当前穿着；叙述层只读取事实，不得自行“记住”或改变穿着。
- 原拟在阶段 5 加入文字衣柜、换装 op/本地操作与互动条件；阶段 5 已收尾，顺延到阶段 6/7 的独立切片。换装查看与选择必须纯本地、零 API。阶段 10 再评估按服饰描述接入可选生图，资产仍遵守 IndexedDB、资产 id/URL 与 zip 导出边界。
- 正式进入 schema 时必须递增版本并附 migration；当前阶段只记录，不提前加字段。

## 角色拥有与使用物品

- 可行。角色自有物品与玩家赠送物品都应由内核库存记录，使用、消耗、归还或展示必须走注册 op / 事件钩子 / 数据包，AI 只写互动文字与提出 ops。
- 送礼当前阶段只记录玩家库存消耗、目标角色、反应和历史；“赠送后归角色持有”和基于物品 tag 的确定性当场互动需要角色库存字段，顺延到阶段 7 与事件系统一起实现。阶段 8 再与住所、职业和生活循环联动。
- 必须防止 AI 虚构角色拥有物品；进入 prompt 的物品事实来自内核，二进制资产规则与玩家物品一致。

## 世界观货币名称与多货币

- 不同世界观可能使用金币、贝壳、信用点、魔晶等不同货币；展示名称不能写死在 UI 或 core 中。
- 阶段 8 经济系统建议由世界/经济配置提供 `defaultCurrencyId` 与 `currencies` 映射，每种货币保存 `name`、可选 `symbol`、`decimals` 和对应的 ASCII `statKey`；余额仍走通用 `stats`。
- 单货币世界保持轻量配置，多货币世界按货币 ID 分开记账。AI 只能叙述经内核确认的金额，不能自行创建货币或改变余额。
- 正式进入 schema 时必须递增版本并附 migration、引用校验和测试；当前阶段只记录设计，不实现经济系统。

## 剧情临时物品与动态目录

- 可行，但不应从自然语言直接提取并写入库存。建议阶段 5/7 评估受限的“注册并发放” op：AI 提出物品名称、稳定 ID、tags、来源和获得理由，内核完成字段长度、重复 ID、来源与单回合上限校验后，在同一事务中写入 `world.items` 与 `player.inventory`。
- 预先定义的 `ItemDef` 仍是常规路径；动态 op 只解决剧情中临时出现的“黄色小花”“旧钥匙”等新物品，并保留来源、可导出性和后续规则匹配能力。注册失败时物品和库存都不写入，正文不自动补偿。
- 阶段 5 结合礼物规则验证候选池与变体；阶段 7 结合事件包验证剧情奖励；阶段 8 再评估角色库存、消耗和生活循环。正式进入 schema 前必须附 migration 与引用完整性检查。

## 收藏型物品、自然语言候选与终端许愿机

- 方向可行：物品栏主要作为玩家的收藏/纪念册，保存名称、描述、标签、来源和获得时间；真正会改变剧情或数值的功能性物品仍由规则、事件和文字叙事控制。建议在数据模型中区分 `collectible` 与 `functional`，避免收藏品意外参与经济、礼物或条件判断。
- 自然语言自动提取可以作为**候选发现**，不能直接写入确定性库存。AI 或本地规则从对话中提出“可能获得的物品”列表，用户逐项确认、编辑名称/描述/tags 或删除后，内核才创建收藏条目。确认前的候选是临时 UI 状态，不进存档；提取失败或误识别不影响正文和正式状态。
- 用户编辑应只修改收藏展示字段；如果条目后来被功能规则引用，删除或改 ID 需走确认/引用检查，不能静默破坏事件、礼物或历史记录。功能性物品仍必须通过明确的注册 op 和效果校验获得。
- 终端可在阶段 9 评估“许愿机” App，作为显式的便利入口：用户输入愿望后先显示预览、影响范围和是否消耗资源，再由用户确认。默认只允许创建收藏型纪念物、重放已解锁内容或提供不改变世界事实的便利；改变金钱、关系、事件进度或功能性库存的愿望必须由世界规则授权，或仅在 sandbox/开发模式开放，并留下可追踪记录。
- 许愿机不应把 AI 当作任意状态写入后门，也不应绕过地图到场、关系阶段和事件条件。若支持“想要一朵黄色小花”，优先生成待确认的 `flower-yellow` 收藏候选；是否是可赠送/可使用的功能性物品，另由阶段 5/7 的规则决定。
- 建议分期：阶段 5 先确定收藏与功能物品的最小结构及确认流程；阶段 7 将候选物品绑定事件奖励和来源；阶段 9 做终端许愿机 UI 与便利规则；阶段 10 再评估本地模型/外部模型辅助提取、批量编辑、导入导出和引用完整性检查。

## 剧情道具与事件回顾

- 收藏物品不应成为剧情逻辑的唯一来源。剧情关键道具、线索和一次性物件可以作为事件包声明的事件事实存在，即使没有进入玩家收藏，事件也必须照常按规则推进。
- 收藏条目可以作为“出示证物”输入：玩家选择已有收藏，内核按角色/NPC、itemId、tags、事件阶段和条件匹配反应；没有匹配规则时只展示，不自动改变状态。AI 只负责描述已经确定的反应。
- 事件结束后保存可回看的 `eventHistory` 记录，包含事件来源、标题、时间地点、参与者、选择、结果摘要和叙事记录。支持导出/删除，删除回顾不回滚世界状态。
- 适合阶段 5 设计证物出示接口，阶段 7 随事件系统实现回顾、导出、删除和长度控制；阶段 10 再评估跨存档整理、搜索和完整性检查。

## 偶遇扩展：移动触发与急事选择

- 角色出门、玩家离开地点或移动途中可以按概率触发偶遇，增加非预期相遇；提供全局开关，用户可以只保留地点到达时的确定性相遇。
- 玩家准备离开地点时，偶遇可以显示“离开”或“留下并继续对方事件”等选择；选择由内核写入事件/关系结果，AI 只负责叙述，不临时改变权重或状态。
- 权重、保底间隔、候选池和开关全部配置化，适合用阶段 2 无头 runner 和固定 seed 回归调参；阶段 4 接入相遇与角色移动后实现。

## 收藏物品的情境化描述与证物反应

- 收藏条目可以按获得时的真实上下文生成标题、描述、tags、来源和时间地点；用户可编辑展示文字、纠错或删除。稳定 ID、所有权、来源和功能标签仍由内核保留，不能因改名而漂移。
- 出示给角色/NPC 时，内核先验证拥有权，再把角色个性、当前情况、事件阶段、物品规则标签和用户确认后的描述交给反应规则/叙述层。同一件收藏品可以因对象不同产生不同反应。
- 用户编辑描述应只影响“对方看到和听到的描述”以及 AI 的措辞，不直接改变功能效果或历史事实；无匹配规则时只产生观察/疑惑类反应，不自动写入状态。
- 阶段 5 实现收藏生成、编辑和基础出示；阶段 7 接入事件上下文和角色状态反应；阶段 10 再评估模型辅助整理、批量纠错和引用完整性。

## Android / iOS 后台与恢复

- 纯前端网页/PWA 无法可靠保活：Android 与 iOS 都可能冻结页面、断开流式请求或回收进程，Service Worker 不能作为常驻生成进程。
- 阶段 9 优先做跨平台可保证的部分：切后台前保存输入、待回复消息和请求状态；返回前台后恢复，并把中断请求明确标记为可重试，避免重复应用 ops。
- 阶段 10 评估移动端壳、系统通知和平台允许的短时后台任务，分别做 Android/iOS 真机验证。不能实现的平台能力必须降级到前台恢复，不宣称后台仍在运行。
- 不引入服务端推送或常驻后端；这会违反纯前端与用户自带 API 的项目边界。
- 阶段 9 可实验默认关闭、单次最长 90 秒的音频辅助开关：仅在请求进行时工作并自动停止，标为“尽力保持”，用 Android/iOS 真机数据决定是否保留。
- Web Worker 不作为保活方案；阶段 10 可实验 Service Worker 代持单次请求并把片段写回 IndexedDB，但其生命周期仍由系统决定，必须保留中断恢复。

## 快照回退后的记忆分支

- 当前阶段快照回退只恢复世界状态，聊天记录保持不变，以避免误删用户内容；这会留下“聊天提到未来事件”的时间线不一致风险。
- 后续可在快照上记录聊天检查点，回退时让用户选择保留聊天、同步截断到检查点，或从该快照新建聊天分支。
- 同步截断必须是显式确认且可预览影响范围；默认不删除聊天。分支与检查点字段应放在独立的本地聊天数据结构中，避免把聊天正文写进世界存档。

## 手机音乐 App

- 可行。终端内可以提供由用户维护的播放列表，音频来源先支持用户自行输入的外链 URL；当前播放曲目、顺序、音量与播放位置属于本地 UI 状态，查看和管理不产生 API 调用。
- 阶段 9 先实现用户显式启动的基础播放、暂停、切曲、列表与 URL 校验；后台/锁屏播放只按浏览器和系统实际支持的能力提供，不承诺所有 Android / iOS 环境持续播放。外链服务需满足 CORS、可读媒体格式和 Range 请求条件，失败时显示明确错误并允许移除或替换链接。
- 阶段 10 再补 Media Session 控制/元数据、可选本地音频导入与离线缓存评估，以及 Android / iOS 浏览器、PWA 和移动端壳真机验证。音频播放不能被暗中用作 API 请求保活机制；保活仍遵守阶段 9 的显式开关与尽力保持边界。
- “一键部署云端 Worker”只有在重新讨论纯前端、密钥仅存浏览器与数据外发边界后才可立项；当前记录为与硬约束冲突，不进入任何阶段。

## 可视化记忆库与话题记忆边界

- TopicTree 的按钮、response 和历史对话是固定内容，不提供“删除话题树后重新生成”的入口。
- 对话过程中经由确定性 op 写入的关系记忆、地点记忆、里程碑或章节摘要，未来可在独立的记忆库中集中查看和管理。
- 记忆库建议支持按角色、地点、类型、游戏日、置顶状态和是否注入 prompt 筛选；每条记录显示来源、发生时间和关联对象。
- 默认操作为“归档/停用”，使条目不再进入未来 prompt 但仍可恢复；永久删除需要显式确认。
- 用户可以编辑记忆正文、展示标签、置顶和注入开关，但不能通过记忆编辑改变稳定 ID、发生日期、地点、关联角色、关系轴、物品、事件或聊天事实。
- 阶段 5 先保证记忆来源和稳定 ID 可追踪，并提供按角色查看、逐条删除的最小入口；阶段 6/7 再实现编辑/归档恢复、筛选、批量管理和导出边界。
- 向量记忆只接外部 embedding API，不在浏览器本地运行模型。阶段 6 先做零 API 的结构化/关键词检索，阶段 7 再提供用户显式开启的混合语义检索；向量只是可重建索引，删除、归档和换模型都必须能排除或重建旧索引。

## 资料与设置图标启动器

- 资料页和设置页功能增多后，阶段 9「有终端」统一改为手机主屏幕/电脑桌面式图标卡入口。
- 每张卡固定显示图标与中文名称，不显示一行状态摘要；底部地图、日程、聊天、资料、设置导航保持不变。
- 阶段 5–8 只稳定分类与入口命名，不提前重排当前页面，避免功能迭代期间反复返工。

## 角色主动靠近玩家的默认基调

- 产品默认体验不是玩家反复试错攻略角色，而是角色逐渐注意、记住、寻找并邀请玩家。
- 忙碌、低落、关系较浅可以影响语气与距离，但默认不转化为无意义的挫败式拒绝；角色可以暂缓，同时留下下一次接触的空间。
- 该方向通过可编辑、可关闭的预设条目实现，不写死进内置格式契约；用户可以自由改成疏离、冲突、敌对或其他叙事氛围。
- 阶段 6–7 可通过晨报、Appointment、事件钩子和 StoryScene 增强角色主动寻找玩家、发起邀约和跨日追逐的表现。

## iOS PWA 安全区与全屏布局

- 当前地图 App 布局继续作为基线：顶栏、右上角工具图标、地图抽屉和底部标签栏不因全屏适配重新排版。
- PWA standalone 适配只处理 `viewport-fit=cover`、`100dvh`、`env(safe-area-inset-*)`、状态栏背景和根背景延伸；普通 Safari 的系统浏览器栏仍不可隐藏。
- 若阶段 4 后的白边只是视觉问题，放入阶段 9 的 PWA 视口兼容切片；若影响点击或内容可读性，再提前作为阻塞性兼容修正。
- 必须在 iOS Safari 标签页、添加到主屏幕后的 standalone，以及 Android 浏览器/PWA 分别验证，不承诺平台无法提供的真正无系统栏全屏。

## StoryScene：轻量剧情大纲与多人电子小说

- 地图相遇保持 1–3 人的日常、陪伴和互动节奏；超过 3 人或需要多阶段推进的内容进入独立 `StoryScene`，避免让偶遇系统承担长篇剧情调度。（分层方向为此前的设计建议。）
- 本轮用户补充：不必先写长文，关键词、短句或几个角色/地点标签即可生成可审阅草案；想精细控制时再填写详细大纲。系统预设采用“选择后复制”的方式，用户可以自由改写而不污染原模板。
- 生成草案只是叙事意图，不是世界事实。用户确认前不启动剧情；确认后仍由内核校验在场角色、地点开放范围、时间、阶段条件和白名单 ops。
- 本轮用户补充：阅读器采用电子小说连续阅读视图，默认护眼主题，支持章节/阶段、选项、进度和恢复；立绘作为可选插图，不能成为多人剧情的硬依赖。
- 规划在阶段 7 实现：阶段 5 记录交互与关系基础，阶段 6 提供世界钩子，阶段 7 的事件池、导演、章节和回顾系统稳定后再落地。若新增存档状态，必须附 schema migration、导入导出和引用完整性测试。
