先给结论：**纯前端可行，技术栈本身不难，真正的难点不在网页，而在"世界状态的数据模型"和"让 LLM 可靠地修改这个状态"。** 你描述的所有功能里，没有一个是做不到的，但有几个如果按直觉的做法做，会在成本和一致性上崩掉——需要换实现思路，不是删掉。

用户自带 API 这个决定帮你省掉了 60% 的工程量：没有后端、没有账号系统、没有计费、没有服务器成本、没有大部分内容合规责任。数据全放 IndexedDB，导入导出用 JSON/zip。这是个非常聪明的定位。

## 一、最关键的架构决策：确定性内核 + AI 只负责文字

这一条决定项目成败，建议第一天就定下来。

把系统劈成两半：

**代码拥有的真实（确定性内核）**：地图图结构、时间、NPC 日程与位置、好感度数值、flags、话题树的已用/未用状态、物品、关系网边权重。这些永远由代码计算，AI 不能直接改。

**AI 拥有的真实（生成层）**：所有叙述文字、对白、场景描写、话题文案、随机 NPC 的设定填充。

AI 不"记住"状态，而是**提议状态变更**。每次回复结尾输出一个受限的操作块，代码校验后执行：

```
<ops>
[
  {"op":"affection","target":"seir","delta":3},
  {"op":"unlock_topic","id":"seir_violin_past"},
  {"op":"set_flag","key":"met_at_docks","value":true},
  {"op":"advance_time","slots":1},
  {"op":"memory","target":"seir","text":"在码头听他提起小时候学琴的事"}
]
</ops>
```

要点：

- op 类型是**白名单注册表**。加新玩法 = 注册一个新 op handler + 在 prompt 里追加一行说明，核心代码不动。这同时也是你"可扩展性"问题的答案。
- 解析必须**容错**：宽松 JSON 解析 + 修复 + 失败重试一次。解析失败时**绝不丢正文**——照常显示叙述，只标记"本回合无状态变更"，给用户手动补录/重试按钮。
- 流式不受影响：正文流式输出，ops 在流结束后解析。
- 提供**调试面板**：显示实际拼装的 prompt（分块可折叠）、原始回复、解析出的状态变化 diff，方便开发与问题定位。
- 可选**两段式**：正文用好模型流式生成，再用便宜小模型做一次结构化抽取。准确率高得多，而且正好落在你"不同功能配不同 API"的设计上。

## 二、地图：用图结构 + 热点图，不要用瓦片地图

强烈建议**不做**可行走的像素/瓦片地图。那需要美术资源、碰撞、精灵动画，会把项目拖进无底洞，而且和 AI 生成天然不合。

推荐方案，两层都做：

1. **图结构（graph）**：节点 = 地点，边 = 路径 + 通行时间。分层：区域 → 街区 → 地点 → 子场景。AI 直接输出 JSON 图，你用 SVG 渲染。风格化的"地图板"（想想《火焰纹章》世界地图、《Reigns》）用 10% 的成本拿到 90% 的空间感。
2. **热点图（hotspot）**：允许用户上传一张自己的地图图片（手绘或 AI 生图），在上面钉节点坐标。实现极简单，但对你说的"给用户留美化空间"是杀手级功能——用户会自己产出好看的地图并互相分享。

节点上挂：绑定的世界书条目、开放时段、标签（室内/室外/商业/住宅）、探索状态（迷雾）、常驻 NPC 槽位。

**迷雾/探索度**建议做：地点初始未知，靠闲逛、听人提起、或被角色带去解锁。这让"闲逛"有回报，成本几乎为零。

## 三、偶遇与动线：这是你的护城河，而且它很便宜

核心机制：**每个 NPC 有一张日程表**（周网格：时段 → 地点 + 活动），由 AI 在角色创建时**一次性生成**，之后由代码执行。

玩家走到某节点时，"谁在这里"是一次**纯代码查询**，不调 AI。只有需要叙述这次相遇时才调 AI，而且把已算好的事实喂进去（谁、在哪、什么时间、正在做什么、好感度、历史摘要）。

这样自然衍生出一堆好玩的东西，全都是低成本高回报：

- **动线追踪**：显示"三天前在码头见过他"的残影标记。
- **情报网**：向 NPC 打听某人行踪，得到模糊线索（"听说他常去旧书店"）。比精确坐标有味道得多。
- **住所邻近度**：每个角色有 `home_node`，玩家有居所。距离直接加权日常偶遇概率——你说的"住到他家附近"就是这一行数学，但情绪回报极强。
- **保底机制**：加权抽取 + "N 天未见"加成，避免天天撞同一个人或永远遇不到想见的人。本质上是抽卡保底。
- **约定系统**：可以和角色约时间地点，写进日历。守约/失约影响好感。非常乙女，且完全复用时间系统。

## 四、话题系统：你的设计是对的，补几个关键点

`require` + `unlock_topic` 双支持、AI 默认生成 require 树、用 `used_topics` 数组判定——这套完全正确，不用改。

补充：

- **给话题加 `terminal` 字段**：区分"纯聊天话题"（可穷举，不推进场景）和"推进型选项"（选了就进下一步）。你的直觉是对的，落地成一个布尔字段就行。
- **一次调用生成整棵树**：进入场景时，一次 AI 调用生成 4-8 个话题及其**简短回应文本**，直接内联在数据里。之后用户点话题是**纯本地渲染，零延迟零成本**。只有用户自由输入或进入深层分支时才再调 AI。这是让话题模式在成本上可行的唯一办法，也顺便解决了延迟体验。
- **说过的话题不要只置灰**：为每个话题缓存一句"我们刚才说过了"的敷衍变体。《心跳回忆》系的手感就在这里——能重问，但会被打太极。
- **日常话题按天刷新，剧情话题永久保留**。否则玩久了角色会"聊干"，显得死掉。
- **自由输入永远和话题按钮并存**。用户打了一句自定义台词，AI 可以反过来 `unlock_topic`。这是必须留的逃生口。
- **隐藏话题显示为 `???`** 的开关你已经想到了，保留。

## 五、NPC 自主生活：改成"被观测时才坍缩"

如果按字面做"NPC 定时自主行动"，每个 tick 给每个 NPC 调一次 API，二十个 NPC 一天四个时段 = 80 次调用/游戏日。用户会立刻烧穿钱包。

改成**惰性求值**：

- 时间推进只跑代码（按日程移动 NPC、好感自然衰减、事件队列出队）。
- AI 只在玩家**实际观测**时才被调用，把那段时间发生的事补写成叙述。
- 保留一个"手动推进世界"按钮和"每 N 回合跑一次世界 tick"选项，给愿意烧 token 的用户。

**NPC-NPC 的幕后对话不要真跑**，改成"传闻/流言"：玩家打听时才生成一段总结。感受上几乎无差别，成本差两个数量级。

**时间用离散时段**（早/午/晚/深夜，或整点），行动消耗时段。别做连续实时——推理简单、成本低、也更像游戏。真实时间联动做成可选开关。

**随机 NPC 转正**：随机 NPC 只存 seed + 模版 + 几条既成事实（轻量记录）。用户"转正"时，AI 把它扩写成完整角色卡并落库。这个流程很干净。

## 六、多 API 路由 + 一个必须提前知道的坑

配置分两层：**Provider**（endpoint / key / model / 参数）和 **任务绑定**（任务 → provider）。任务至少划分：主线叙事、日常对话、世界生成、地图生成、结构化抽取、摘要压缩、NPC 模拟、生图、语音。

除了内置 OpenAI / Anthropic / Gemini 适配，一定要做一个**通用适配器**：让用户自己填请求模板和响应取值路径（JSONPath）。这样任何新服务用户自己就能接上，不用等你发版。

**坑：CORS。** 浏览器直连很多厂商的 API 会被拦。OpenAI、OpenRouter 允许；Anthropic 需要显式带 `anthropic-dangerous-direct-browser-access` 头；不少第三方中转和本地推理服务需要自己配。解决路径：文档里明确说明 + 提供"连接测试"按钮给出可读的错误诊断 + 后期出一个 Tauri 桌面版（顺便解决文件读写和存储配额）。这个问题不解决，你会被大量"为什么连不上"的反馈淹没。

另外要在 UI 里明说：key 存在浏览器本地，别在公共设备上用。

## 七、可扩展性：能做到，但只有第一天就定架构才能做到

具体到五件事：

1. **所有数值走通用 key-value**，不要硬编码字段。角色不是 `{affection: number}` 而是 `{stats: {affection: 42, trust: 10, 用户自定义的任何东西: 3}}`。你的"用户自行设计系统规则"需求，本质就是需要泛化的 stats + flags + 条件表达式。
2. **条件用安全表达式求值器**（比如 expr-eval 之类，绝对不用 `eval`），效果用小型 effect DSL。用户就能纯靠数据定义经济、声望、阵营系统。
3. **事件总线 + 命名钩子**：`onEnterLocation` / `onTimeAdvance` / `onEncounter` / `onDialogueEnd` / `beforePromptAssemble` / `onOpsApply`。以后加功能都是订阅钩子，不是改核心。
4. **Prompt 拼装做成有序可注入的 block 列表 + 优先级 + token 预算分配**。新功能加 block，永不重写拼装器。超预算时按优先级截断。
5. **第一天就写迁移框架**：每条存档带 `schema_version`，迁移是一串函数。没有这个，你以后每次"灵光一闪"加功能都会炸掉老用户存档——这是这类项目最常见的死法。

美化层：CSS 变量 + 用户自定义 CSS 注入 + 关键组件（消息气泡、地图、手机）支持模板覆写。

## 九、我想补充的两个设计（续）

### 1. AI 导演（事件调度器）

根据好感度、flags、距上次剧情的天数、当前地点标签，从一个"事件池"里挑事件塞进未来的时间槽。事件可以是纯数据（条件 + 触发内容），也可以让 AI 现场生成一个。

关键在**节奏控制**，几行逻辑就能做出质变：

- 事件之间设冷却，避免天天出大事
- 好感区间门槛：低好感不触发告白线，高好感不再出"初次见面"式桥段
- 张力曲线：连续几天平淡后主动抬升
- **pending 事件队列**：导演可以"预约"三天后在某地点发生某事——这就产生了伏笔感

有导演和没导演的区别，就是"随机遇到人"和"故事正在发生"的区别。而且它天然数据驱动，用户可以自己写事件包分享。

### 2. 别让开放世界变成空沙盒

这是我认为你项目**最大的设计风险，比任何技术问题都大**。"想做什么就做什么"在实际体验里经常变成"不知道该做什么"——用户逛两圈发现没事干就关掉了。开放世界游戏靠美术和玩法填充这个空洞，你没有这些资源。

所以要给"生活"装骨架，不是任务列表，而是低强度的持续驱动力：

- **生计压力**：定期房租/结算。金额小、不致死，但构成节奏锚点。它让"打工"有意义，也让"当无业游民"成为一个真实的选择而不是默认的空白。
- **玩家自己的日程**：上班时段、店铺营业时间。有约束才有"翘班去见他"的戏剧性。完全自由的玩家没有故事。
- **三条常驻软目标**：住所升级、关系推进、事业线。保证任何时刻都有事可做。
- **每日结算页**：今天遇到了谁、好感变化、收支、日记。给一天一个收束点，这也是玩家感知"我在生活"的地方。

一句话：**约束创造生活感，绝对自由创造空虚。**

## 十、难度评估

技术栈建议：React + TypeScript + Vite，Zustand 管状态，Dexie 封 IndexedDB，SVG 渲染地图，zod 做数据校验，expr-eval 求值条件，Tailwind + CSS 变量做主题，JSZip 做导入导出。后期 Tauri 打桌面版。全静态，Cloudflare Pages / Vercel 免费托管。

按模块给个粗略难度（满分 5）：

| 模块 | 难度 | 备注 |

| 流式聊天 + 多 provider | 2 | CORS 是主要摩擦，不是代码难 |
| 角色卡 / 世界书 / 预设 + 导入导出 | 2 | 项目原生 JSON / zip 格式 |

| 话题树 | 2 | 你的设计已经能直接实现 |
| **记忆 / 摘要压缩** | **4** | 全项目最难保证质量的部分 |

| 手机终端 UI | 2 | 性价比最高的模块 |

## 先说几个判断

天数制不只是换了个计时单位，它顺手解决了三个原本很难的问题，这个收益比你预想的大：

- 记忆压缩有了天然切点。ST 按楼层摘要，永远会切在场景中间，导致角色性格漂移。按天切，每天结算生成一篇日记，原始对话就可以丢掉。长期上下文 = 角色卡 + 关系摘要 + 最近 7 天日记 + 重要事件里程碑，更老的压成周摘要、章节摘要。这是全项目最难的部分，被日结构直接摆平了一半。
- 存档变简单。每天结算自动快照，"回到第 12 天"比 ST 的分支楼层直观得多，数量也可控。
- 节奏可控。导演往未来的日历格子里填事件就行，可视化就是一个日历，甚至能给玩家看到模糊预告（"三天后有拍卖会"）。

另外一个关键点：把移动设成消耗时段。一天分 4–6 个时段，走远路花时段，这样地理才有重量，"住到他家附近"才不是文案而是数学。地图能不能立住，全看这一条。

## NPC 调用：把晨报和世界脉动合并成一次调用

你的方向对，但可以更省。分三层：

| 层级 | 内容 | 调用方式 |
|---|---|---|
| 正式角色 | 完整卡、独立记忆、独立日程 | 玩家实际互动时单独调用 |
| 半正式 NPC | 名字 + 几条既成事实 + 轻记忆 | 打包进每日一次调用 |
| 背景 NPC | seed + 模版，无记忆 | 现场生成，不落库 |

然后把"晨间报纸 + 半正式 NPC 动向 + 天气 + 世界微变"合成一次「晨间世界更新」调用。一游戏日一次，覆盖整个后台世界。正式角色不需要每天调用，他们的幕后生活在被观测时按日程反推即可。

报纸里建议混四种条目：硬线索（指向具体地点+时段，去了触发事件）、软氛围（纯世界观调味）、角色相关（"某乐团首席近日频繁出入旧城区"）、伪装成广告的系统入口（招聘、租房、店铺转让——你的经济和职业功能就靠这个露头，不需要额外菜单）。

两个细节让它质变：一是让报纸有回声，把昨天的日记塞进 prompt，玩家在码头打了架，第二天就有"码头骚乱"，世界立刻显得在看着你，成本为零。二是未被选中的钩子放回池子，几天后重现或过期（"上周的失踪案已结案"）。过期带来的"我错过了什么"是好东西，别修。

形式随世界观换皮：报纸、公会委托板、终端推送、酒馆流言、鸽信，底层是同一个模板。

## 关系模型：数值要隐藏，但不能取消

你对好感度的不满是对的，一个标量确实表达不了乙女向的关系。但如果完全取消机器可读的关系状态，玩到第 40 天必然漂移——AI 记不住"我们现在算什么关系"。正确解法是隐藏和拆分，不是删除。

建议拆成几条可独立移动的轴：亲密（愿意共享多少私人空间）、信任（愿不愿示弱、依赖）、张力（心动/暗流）、熟悉度（单调递增）。关键是它们可以反向：亲密高而信任低，就是"贴得很近但始终防着你"，这恰好是最好写的乙女状态，单个数字表达不出来。

然后从这组轴 + flags 推导出一个关系阶段标签：陌生人 / 面熟 / 熟人 / 朋友 / 知己 / 暗流 / 恋人 / 决裂。进 prompt 的是标签，不是数字，AI 读到的是"你和他现在是熟人，但存在未言明的张力"。数值默认对用户隐藏，在结算页写成散文（"他今天似乎比平时多说了几句话"），设置里给个开关让想看数字的人看。

这样你开头那个问题自动消失：角色卡里可以直接把初始值设成亲密 60 / 信任 20，"一登场就很热络但根本不信你"是合法配置，不是数值 bug。轴的名称和数量交给用户扩展（依赖、敬畏、嫉妒随便加），复用通用 stats。

有一点要反驳你：只用性格 + 当前关系不够。同一个角色在同一阶段，每次相遇会读起来一模一样。至少还要两项：当前情绪（一个词 + 几天衰减）和当下处境（正在做什么、忙不忙）。这两个才是"活着"的来源，而且极便宜。

还有一个天数制的免费红利：记录上次见面日期，prompt 里写"你们已经 23 天没见"，AI 自己会处理情绪含义，不用新增任何数值。同理，关系不应只单调上升，加"心结"flag，不处理就一直在。

## 地图作为核心，具体怎么挂

- 世界书绑定节点，进入即注入。这比 ST 的关键词触发精确得多——位置决定上下文，是你相对 ST 的实质改进。
- 地点也有记忆。每个节点存 3–5 条痕迹（在这里第一次见到他、在这里吵过架），重访时注入。"老地方"的情绪是乙女向最有效的机制之一，实现成本几乎为零。
- 手机只能维持关系，不能推进关系。深度剧情必须到场。这条规则用机制保证了"走出去"这个立意不被手机架空。夜里可以收到主动来信（分开后还在想你，情绪价值极高），但不解锁重要节点。
- 开店/打工绑定到节点并占用时段，于是玩家自己变成地图上的一个点，角色会路过来找你。这是反向偶遇，比出门找人更动人。
- 物品记录获得地点，礼物、回忆、商店都挂在节点上。
- 事件三元组统一为（地点，天，时段），导演往日历里排。
- 天气每天一行数据，注入 prompt，还能门控事件（雨天特殊相遇）。便宜到不做很亏。
- 多人同场时要在 prompt 里明确要求角色之间互相说话，而不是轮流对玩家汇报；并且当着别人在场时该说不出某些话。三角关系素材免费拿。
- 不是所有互动都成功。忙、心情差、关系不到位就该被拒绝。纯代码可判定，让成功有分量。

## 一天的固定仪式

晨报 → 选择行动（花时段）→ 移动 / 相遇 / 剧情 → 夜间结算 + 日记 → 睡觉进下一天。

固定循环让玩家知道该干什么，但每天内容不同。这个仪式感是"在生活"和"在用聊天软件"的分界。结算页里放：今日足迹、遇到了谁、关系变化（散文）、收支、新物品、日记、明日待办与约定。

约定系统是天数制最大的受益者：（角色，日期，时段，地点）四元组，守约、迟到、失约。几乎不用写代码，但它给了玩家"想活到明天"的理由。

每 N 天或达成条件收束成一章，生成章节回顾，同时充当二级记忆压缩。

## 行动点：可自定义，但要分清哪一层能改

关键是别把它设计成"每天 N 点"这一个数字，而是拆成两层：

**时段**是世界时钟单位，NPC 日程、事件排程、商店营业时间全都以它为坐标。**成本表**规定每个行动吃掉几个时段。于是"每天能做几件事"不是一个独立参数，而是时段数除以平均成本的结果——用户想更悠闲，可以加时段也可以降成本，两条路都通，你不用为此写任何特殊逻辑。

成本表完全数据驱动，随时可改。时段数则要在建世界时定下来，因为 NPC 日程是 `slotId → location` 的映射，中途从 4 改成 6，所有角色日程会出现空洞、事件日历会错位。实现上把时段定义存成世界配置里的数组（`{id, 名称, 显示时间}`），日程引用 id 而不是下标；然后开局后默认锁定，设置里留一个"高级：重映射时段"的向导，并明确警告会影响已有存档。

## 一条比数值更重要的原则：相遇不收费

```
跨区域移动        1
同区域内移动      0
打工一班          2
探索未知地点      1
休息/发呆         1
剧情事件          由事件自己声明（1–2）
偶遇与日常对话    0
```

移动和"占据时间的活动"收费，**交互本身不收费**。这个项目的立意是走出去，如果每次搭话都要算点数，玩家会开始算计、不敢乱逛，探索欲直接死掉。同理，看地图、翻手机、查物品栏、读日记、点已生成的话题、在同一地点跟人聊多久，全部免费。玩家付的是"选择去哪里"的代价，不是"要不要开口"的代价。

顺带一提，这条原则和上次讲的成本控制高度重合——免费的基本都是纯本地渲染、不调 API 的操作。

## 预设三档 + 一个开关

悠闲 6 时段 / 标准 4 / 紧凑 3，建世界时选，之后可微调成本表。

另外强烈建议加一个**无限时段沙盒开关**。有一批用户就是想纯聊天、不要任何管理压力，这个开关实现成本为零，但能留住他们；反过来喜欢压力的人可以调到 3 时段配房租。你的"用户自定义规则"定位在这里第一次真正兑现。

体力这类第二资源我建议放到阶段 8 再说。它确实能造出"明知会累还是翘班去见他"的张力，但双资源会立刻抬高理解门槛。留个钩子就行：体力就是普通 stat，成本表加一列 `energyCost`，将来开箱即用。

最后，时段用完不该是失败状态，只是机会成本。早睡要允许，并且给点小回报（回体力、第二天状态好），让"今天就这样吧"成为一个真实的选择。

## 关于转 agent

对，该转。聊天客户端的问题不是写得慢，而是它读不到你的仓库、跑不了 build、跑不了测试、发现不了自己写错。agent 的核心价值在于闭环：改完能编译、能跑起来、报错能自己回头修。这个项目后期最耗时间的就是 prompt 调试和参数手感，全靠反复跑，没有闭环会非常痛苦。

## 立绘：把它做成"资产层"，不是角色卡的一个字段

这个功能本身不难，但有一件事必须第一天就定：**存档里只存资产 id，二进制放 IndexedDB，导出时打包进 zip**。如果早期图省事把 base64 塞进角色 JSON，后面内存和导出体积都会炸，而且改这个要写迁移。

数据形状大概是：

```ts
type AssetRef = { assetId: string } | { url: string };  // 也允许外链,零存储

interface PortraitSet {
  id: string;                              // "default" | "winter" | "uniform"
  name: string;
  expressions: Record<string, AssetRef>;   // 键名用户可自定义
  transform?: { scale: number; offsetX: number; offsetY: number };
}

interface CharacterVisuals {
  avatar?: AssetRef;          // 地图图钉 / 手机联系人 / 消息头像
  portraitSets: PortraitSet[];
  activeSetId?: string;
  defaultExpression: string;
  accentColor?: string;       // 无立绘时的名牌配色
}
```

几个关键点：

**回退链**是"没有立绘也能玩"的实现方式，不是特殊分支：请求的表情 → 当前套装的 default → 角色的 defaultExpression → avatar → 名牌占位。缺图时永远降级到上一级，不报错、不空白。占位要做得像有意设计的——角色专属配色的名牌 + 首字母，配上排版就够体面了。

**AI 换表情**走 ops，但表情建议支持流式内联标记，因为它需要在一段话中间变：

```
{"op":"portrait_set","target":"seir","set":"winter"}    // 换套装,较少发生
正文里内联 [[seir:blush]]                                 // 表情,渲染时剥掉
```

这里有个坑必须处理：**prompt 里只列出该角色实际拥有的表情名**（从资产动态生成），再加一层别名映射 + 模糊匹配回退。否则 AI 会输出 `shy` 而你的文件叫 `blush`，一半时间点不中。没有立绘的角色，同一个表情 op 可以退化成名牌染色或一句括号动作，体验不掉档。

**多人同场**照抄视觉小说语法：最多三个位置，说话者高亮，其他人压暗缩小。每个角色存自己的 transform，这样不同画师、不同尺寸的图也能对齐基线——用户混用素材时这个是必需的。

**导入时提供降采样选项**（限制最大高度、转 webp）。图片是唯一会让存储配额出问题的东西，顺手请求一下 `navigator.storage.persist()` 降低被浏览器清理的风险。导出角色包时给一个"含图 / 仅引用"开关，方便用户分享自己无权再分发的素材。

排期上，头像在阶段 4 就需要（地图图钉），表情和站位放阶段 5，但 AssetRef 这个格式和 zip 打包约定要在阶段 0 的存档结构里就写进去。
